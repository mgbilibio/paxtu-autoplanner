Instrucoes de Codigo

Atualizado em 20260904-2048 (versão 2026.9.8). Aplicam-se ao app alvo em PaxtuAP/.

Arquitetura atual

  • src/: interface React e regras de apresentação.
  • electron/: processo principal, IPC e acesso controlado a arquivos/PDFs.
  • src/services/storage/: persistência local e em pasta compartilhada; storageService.ts é a fachada pública.
  • conhecimento/bd/: bancos SQLite auditáveis de progressão, especialidades e biblioteca.
  • src/data/generated/: derivados TypeScript dos bancos. Não editar manualmente.

Fonte normativa e catálogo

  • progressao_2025.sqlite contém 18 blocos, 80 ações fixas, 230 variáveis e os reconhecimentos oficiais de Lobinho e Escoteiro. Metadados de ramo revisados em 2026-08-09: Lobinho 6,5-10,5 anos; Escoteiro 10-14 anos.
  • conhecimento/especialidades/2026_ueb_atualizado/especialidades_ueb_2026.json contém 208 especialidades e 1.385 requisitos capturados da página pública UEB em 2026-08-11.
  • src/data/updatedSpecialtyCatalog.ts adapta a base UEB 2026 para códigos estáveis ESP-UEB26-<id>, usados pelo catálogo POR 2025+, enciclopédia, fichas e agenda.
  • especialidades_guia.sqlite contém 274 especialidades e 2.741 requisitos do catálogo 2024-1, hoje preservado como programa anterior/transição.
  • src/data/officialSpecialtyCatalog.ts mantém compatibilidade com fichas 2024-1 ESP-GUIA-<id> e também reconhece ESP-UEB26-<id> em fluxos legados que chamam essa função.
  • specs_*.json e as regras de premiação antigas são compatibilidade do POR 2020, não fonte de verdade do POR 2025+.
  • Antes de alterar requisitos, blocos, insignias ou reconhecimentos, conferir fonte oficial atual. Para especialidades UEB 2026, regenere a base com python conhecimento/tools/scrape_ueb_especialidades_2026.py e valide requisitos vazios antes de integrar.
  • Resoluções CAN 05/2025 e CAN 09/2025: transição do Programa Educativo atualizado até 30/06/2027; obrigatoriedade geral em 01/07/2027; Paxtu/mAPPa/cONdecora atualizados a partir de 01/02/2026.

Regras de persistência

  • Ações de bloco usam MemberBlocoState.
  • Especialidades usam MemberSpecialtyState, por requisito, com evidência, status e avaliador.
  • O lançamento pela agenda marca ações de bloco e inicia especialidades. Nunca deve concluir automaticamente os requisitos de uma especialidade.
  • ProgressLaunchApply.codesApplied registra o que o lançamento aplicou fisicamente; codesCredited registra o que foi creditado mesmo quando já existia. Reversões devem consultar outros lançamentos ativos antes de remover estado do jovem.
  • Excluir evento de agenda com lançamento vinculado deve passar por deleteProgressLaunchAndReverse, evitando lançamento órfão e preservando créditos sustentados por outra atividade.
  • Preservar os registros legados SP-* e PAXTU_PROG_*; não os misturar com o fluxo POR 2025+.

Segurança de IA e backup

  • Backups locais devem limpar todos os segredos da configuração, incluindo apiKey e ollamaCloudApiKey, também na importação.
  • O IPC ollama:request só deve anexar Authorization após validação por URL parseada e host cloud allowlisted.
  • Ollama Cloud não deve iniciar chamadas JSON com format=json; use prompt estruturado e parser/fallback do app.

OAuth xAI/Grok

  • A edição web usa Device Authorization Grant, reaproveitando o fluxo comprovado do projeto SocialKids.
  • xaiOAuthDevice.ts inicia e acompanha a autorização; xaiOAuthSession.ts mantém access e refresh tokens somente no sessionStorage.
  • Tokens xAI nunca devem ser gravados no Firestore, localStorage, logs, configuração exportada ou repositório.
  • O Worker em workers/xai-proxy encaminha device, token, userinfo, language-models e chat/completions. Origens: https://mgbilibio.github.io e localhost. Nunca funciona como proxy aberto. Respostas 403 levam cabeçalhos CORS para o browser não esconder o erro como “Failed to fetch”.
  • A URL do Worker entra no build por VITE_XAI_PROXY_URL (variável pública do GitHub Actions, não secret). Sem ela, ou se o Worker estiver fora, a UI avisa em português. Em desenvolvimento, /__xai_oauth no Vite é o fallback same-origin. Não colocar tokens, client secrets ou chaves privadas nessa variável.
  • O indicador Gemini/Grok no chrome reusa hasGeminiCredentials, getXaiBrowserStatus e sondas leves de listagem. Verde só se a credencial for utilizável agora.
  • O Client ID do Device OAuth é público (app Pages). Tokens só em sessionStorage. Não há client secret no repositório.
  • No desktop, OAuth usa o cliente Grok Build (electron/grokClient.ts). Sem o binário, o status não afirma que o login funciona.
  • O provider aceita a sessão OAuth ou uma chave API opcional. Ambos consultam /v1/language-models em tempo de execução.

Catálogos de modelos

  • Gemini deve consultar models.list e aceitar somente modelos anunciados com suporte a generateContent.
  • A preferência Flash-Lite/Flash é uma regra por capacidade e custo. Uma lista curta de fallback (GEMINI_FALLBACK_MODELS) existe só para cold start / falha da listagem — não é o catálogo completo.
  • Sem credencial ou se a listagem falhar, o seletor mantém o padrão Flash-Lite. A geração continua exigindo chave/token e avisa.

Responsividade do shell

  • O cabeçalho usa breakpoint amplo para trocar por menu compacto antes de a navegação ficar apertada.
  • Itens de navegação e abas de Configurações aceitam quebra de linha; não usar larguras fixas que cortem rótulos em telas estreitas.

Contrato do gerador de atividades

  • scheduleDraft é a fonte única de ordem, quantidade e duração. Não criar lista paralela de atividades na interface.
  • ActivityEditor mantém visíveis nome, responsável, objetivo curto, descrição detalhada, materiais, progressão e informações para a chefia.
  • Preparação, segurança e referência documental ficam recolhidas. Campos avançados antigos continuam compatíveis, sem preenchimento obrigatório.
  • buildManualMeetingPlan salva sem credencial de IA. Só nome, descrição e materiais bloqueiam; referências inaplicáveis geram aviso.
  • A IA é secundária e preserva a ordem, o título, a duração e o responsável do cronograma. Nunca inventar código ou fonte. Quando a IA gerar, o conteúdo de campo (letra, cartões, script, roteiro cronometrado) continua obrigatório no tipo correspondente.

Validação e release

  1. npm test.
  2. npm --prefix workers/xai-proxy test.
  3. npm run build:web.
  4. Publicar a main e confirmar o workflow GitHub Pages.
  5. Testar login, catálogo e geração no site implantado.

O produto-alvo é a edição web com Firebase e deploy pelo GitHub Pages. O build usa Vite 8; em vite.config.ts, use import.meta.dirname no lugar de __dirname. Os filtros de especialidade devem usar isSpecialtyCode, jamais o texto visível da categoria. Atualize este documento, usersmanual.html e versions.html em qualquer alteração de comportamento, dados ou distribuição. Os originais HTML da UEB ficam em docs/biblioteca/fontes_web/ueb_especialidades_2026_08_11/; versionar manifesto/hashes, não o cache bruto.
